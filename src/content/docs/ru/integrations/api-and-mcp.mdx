# REST API и MCP

REST API предоставляет документированные операции с ресурсами и использует аутентификацию через session, API token или OAuth в зависимости от сценария. Remote MCP предоставляет ориентированные на задачи инструменты с теми же областями, валидацией, правами по тарифу и audit trail.

Автоматизация должна:

- использовать отдельную идентичность с минимальными правами;
- считать `202` или создание Task принятием работы, а затем опрашивать долговечное состояние;
- повторять только идемпотентные операции или использовать контракт retry конкретной операции;
- раздельно обрабатывать `401`, `403`, `409`, `422` и сбои offline Node;
- не разбирать текст UI, когда существует структурированное поле API;
- фиксировать resource IDs и request IDs, не записывая секреты.

Используйте документ OpenAPI, который отдаёт работающий экземпляр Gateway, для точных схем запросов и ответов. Версия схемы должна совпадать с автоматизируемым экземпляром; не копируйте тела запросов из другого релиза. Руководства продукта описывают необходимый порядок ресурсов и эксплуатационные последствия, которые нельзя выразить одной схемой.

## Аутентификация и обнаружение

Выберите session, API token или OAuth client в соответствии с вызывающей стороной. Клиенты Remote MCP авторизуются через OAuth и обнаруживают ориентированные на задачи инструменты, отфильтрованные теми же областями и состоянием продукта. Наличие инструмента не доказывает, что конкретная мутация ресурса будет допущена.

Начинайте автоматизацию с чтения целевого ресурса и состояния capability. Разрешайте стабильные IDs, а не извлекайте имена из UI. Храните base URL, токен и environment раздельно, чтобы скрипт разработки не мог случайно обратиться к production.

## Долговечные операции

Многие мутации инфраструктуры возвращают принятую Task или операцию, а не завершённый результат:

1. отправьте проверенный запрос;
2. сохраните возвращённые IDs ресурса, Task, операции и запроса;
3. опрашивайте долговечное состояние операции или подпишитесь на него;
4. изучите структурированные сведения об ошибке;
5. независимо проверьте итоговое состояние ресурса;
6. повторяйте только согласно контракту идемпотентности операции.

Не превращайте transport timeout напрямую во второй запрос create/delete. Первый запрос мог достичь владеющего daemon и ожидать реконсиляции.

## Обработка ошибок

- `400` или `422`: исправьте форму запроса или входные данные валидации;
- `401`: обновите или замените аутентификацию;
- `403`: отличите отсутствующую область от отсутствующего права по тарифу;
- `404`: проверьте видимость ресурса, а не только его существование;
- `409`: проверьте конфликт жизненного цикла, quota или текущее состояние;
- `429`: примените ограниченный backoff и следуйте указаниям сервера;
- `5xx` или offline Node: сохраните request IDs и проверьте состояние долговечной Task до повтора.

## Правила работы MCP

Используйте MCP для ориентированных на цель операций, где схема инструмента добавляет безопасность и контекст ресурса. Читайте описания инструментов и возвращаемые предупреждения, передавайте точные идентификаторы ресурсов и считайте внешний контент недоверенным входом. Вызовы MCP фиксируются в аудите и не должны использоваться для обхода подтверждений, прав, entitlements или проверок жизненного цикла.

## Проверка

Для каждого пути автоматизации проверьте одно разрешённое действие, одно запрещённое действие, одну ошибку валидации, один асинхронный успех и одну прерванную операцию. Подтвердите атрибуцию аудита и убедитесь, что логи маскируют учётные данные и чувствительные поля запросов.
