**Node** — это Linux-хост, зарегистрированный в Gateway для определённой эксплуатационной роли. На хосте работает управляемый Gateway daemon: он сообщает identity и capabilities и принимает только команды, разрешённые для этой роли. Добавление Node не переносит существующие workloads автоматически; оно создаёт доверенную ёмкость, которую можно выбрать позднее.

Ожидаемый результат прост: Node отображается **Online**, сообщает правильную роль и capabilities и восстанавливает соединение после restart службы или хоста. Platform owner выбирает роль и security boundary; host operator запускает одноразовую команду установки и проверяет локальные prerequisites.

## Выберите роль до enrollment

| Роль | Назначение | Главное решение владельца |
| --- | --- | --- |
| **Ingress** | Routes, материализация TLS, Pages, nginx logs и traffic metrics | Какие публичные адреса и порты принадлежат хосту |
| **Docker** | Containers, Deployments, Compose Projects, images, volumes, networks и runtime operations | Какие workloads могут совместно использовать Docker-хост |
| **Databases** | Gateway-managed PostgreSQL, Redis и ClickHouse | Storage, backup и изоляция stateful workloads |
| **Build Worker** | Изолированные Git-source builds через BuildKit/containerd | Build egress и отделение от reusable credentials |
| **Monitoring** | Поддерживаемый сбор мониторинга | Какие системы Node разрешено наблюдать |
| **Relay** | Ёмкость и устойчивость Secure Link data plane | Доступный advertised address и физический fault domain |

Не выбирайте роль только потому, что её installer запускается на хосте. Production-роль должна соответствовать назначению host, trust boundary, network placement, storage и recovery owner. Build Workers и database Nodes обычно должны быть выделены под своё назначение.

## До создания Node

Убедитесь, что цель — поддерживаемый Linux-хост с root-доступом или работающим `sudo`, корректным системным временем, надёжным DNS и исходящей доступностью Gateway public gRPC target на `9443/tcp`. Это Relay-backed control endpoint для управляемых daemons; он может быть прямым host или IP даже когда веб-интерфейс Gateway находится за proxy.

Также подтвердите ownership для роли:

- Ingress Nodes требуют нужных public listeners и понятной модели DNS/TLS.
- Docker Nodes требуют локальный поддерживаемый Docker Engine и достаточную ёмкость; Node installer может подготовить поддерживаемые runtime components на свежем совместимом хосте.
- Database Nodes требуют подходящее постоянное хранилище и loop/mount capabilities. Не считайте обычный ограниченный LXC guest заведомо достаточным.
- Build Workers требуют отдельный хост или внешний unprivileged container и утверждённый egress profile.
- Relay Nodes требуют адрес и порт, доступные участвующим Gateway, Docker, Ingress и database hosts. Gateway не открывает firewall и не выполняет NAT traversal.

## Зарегистрируйте Node

1. Откройте **Nodes** и выберите **Add Node**.
2. Выберите нужную роль. Для Relay укажите адрес, по которому другие участники будут достигать Relay worker.
3. Дайте pending Node понятное имя, описывающее его стабильное назначение, а не временную задачу или человека.
4. Создайте Node и скопируйте сгенерированную installer-команду. Она содержит одноразовый enrollment token и ожидаемый fingerprint сертификата Gateway.
5. Выполните команду на целевом хосте с нужными privileges. Не удаляйте fingerprint и не меняйте Gateway address, если только настроенный public/local target действительно неверен.
6. Сохраните вывод установки, пока daemon не завершит enrollment и UI Gateway не покажет Node **Online**.
7. Откройте Node details и сравните hostname, role, operating system, version, addresses и capabilities с утверждённой схемой.

Daemon проверяет закреплённый сертификат Gateway до отправки одноразового token. После успешного enrollment долговременная аутентификация использует mutual TLS: Gateway и Node предъявляют сертификаты друг другу. Постоянной связью является зарегистрированная identity, а не bootstrap token.

## Критерии успеха

Считайте enrollment завершённым только если:

- Node находится **Online**, а не просто создан или pending;
- type и hostname правильные;
- reported version совместима с релизом Gateway;
- ожидаемые capabilities присутствуют и предупреждения version mismatch нет;
- role-specific status healthy;
- Node подключается снова после restart daemon service;
- встроенная проверка обновлений достигает настроенного release channel;
- назначенный operator имеет scopes для просмотра и управления без широкого system-admin доступа.

Для Relay успешный enrollment делает physical host доступным для Relay Pool. Добавление healthy Relay не переносит существующие endpoints автоматически; проверьте reachability и используйте явную операцию rebalance, когда действительно хотите изменить placement.

## Проверки оператора по ролям

- **Ingress:** проверьте nginx configuration, service address, порты 80/443 при необходимости и ограниченный фрагмент nginx logs.
- **Docker:** проверьте inventory synchronization, runtime status, filesystem access и ожидаемые GPU или Secure Runtime capabilities.
- **Databases:** проверьте выбранный storage root, enforcement ёмкости и завершение preflight до создания managed database.
- **Build Worker:** проверьте BuildKit/containerd health, enforced resource profile, доступность scanner и выбранную egress policy.
- **Relay:** проверьте supervisor и worker health, advertised endpoint, число active tunnels и fault-domain placement.

## Сбой и безопасное восстановление

Если enrollment не завершается, сохраните pending Node на время диагностики. Проверьте точную сгенерированную команду, системное время, DNS, исходящую доступность `9443/tcp`, fingerprint сертификата, installer log и daemon service log. Cloudflare-proxied web hostname не становится автоматически подходящим gRPC target.

Не удаляйте certificate pinning ради успешного подключения. Это превращает configuration problem в identity risk. Если public или local gRPC target указан неверно, исправьте **Settings > Gateway > General** и сгенерируйте новую команду.

Pending Node можно удалить и создать заново, когда вы намеренно выпускаете новую enrollment identity. Никогда не используйте старый one-time token повторно. После enrollment удаление имеет role-specific последствия: Relay с active assignments нужно drain, а Node с workloads или данными следует выводить через соответствующий workload/database runbook, а не просто удалять из inventory.
