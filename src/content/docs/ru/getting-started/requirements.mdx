Планируйте плоскость управления отдельно от хостов, на которых выполняются пользовательские рабочие нагрузки. Gateway координирует идентичность, желаемое состояние, сертификаты, операции и историю аудита, но не отменяет необходимость рассчитывать ресурсы, обновлять, резервировать и наблюдать за базовыми Linux-хостами.

## Определите схему развёртывания

Для небольшой оценки приложение Gateway и его внутренние службы можно разместить на одном Linux-хосте. В production этот хост всё равно следует считать зависимостью плоскости управления: у него должны быть явный владелец, постоянное хранилище, процедура восстановления и контроль ёмкости. Роли управляемых рабочих нагрузок подключаются позднее и могут находиться на отдельных физических серверах, виртуальных машинах или достаточно изолированных системных контейнерах.

До установки зафиксируйте:

- канонический HTTPS URL, которому будут доверять пользователи и управляемые Nodes;
- владельцев DNS, сертификатов, аутентификации, резервного копирования и обновлений;
- сети, из которых доступны веб-приложение и Relay;
- роли Nodes, нужные сразу, и роли, которые можно добавить позднее;
- требуемый тарифный план и права на функции;
- целевые показатели восстановления данных Gateway и материалов шифрования.

Не стройте схему вокруг временного IP-адреса или hostname, который планируется переименовать после запуска. Канонический URL участвует в защите браузера, redirect URI, сгенерированных командах и интеграциях.

## Решение по хосту и ёмкости

Предоставьте поддерживаемый Linux-хост с root-доступом или работающим `sudo`. Docker не является prerequisite публичного установщика: если Docker Engine или Compose v2 plugin отсутствует, установщик сам устанавливает и настраивает их из официальных package repositories Docker. Автоматическая установка Docker поддерживает семейства Debian, Ubuntu, Fedora, CentOS и RHEL. Если Docker уже установлен, установщик проверяет доступность engine и Compose v2.

Используйте базовые профили sizing для плоскости управления:

| Профиль | CPU | Память | Свободное место на SSD |
| --- | ---: | ---: | ---: |
| Минимальный | 2 vCPU | 4 GB RAM | 32 GB |
| Рекомендуемый | 4 vCPU | 8 GB RAM | 64 GB |

Объём диска означает свободное место после установки ОС. Для Gateway-managed local ClickHouse logging дополнительно требуется минимум 32 GB или рекомендуется 128 GB; фактический расход зависит от ingest volume и retention. External ClickHouse не добавляет локального logging storage на хост Gateway.

Выделите постоянное хранилище для PostgreSQL Gateway, persistence Redis, если она включена, загружаемых артефактов, сертификатов, конфигурации, внутреннего registry и необязательных структурированных логов. Git-source builds требуют дополнительной ёмкости registry, поскольку сохраняются успешные, active, rollback, in-progress и вручную закреплённые артефакты.

Также как минимум обеспечьте:

- запас CPU и памяти для приложения, PostgreSQL, Redis и Relay без постоянного давления swap;
- постоянное хранилище с мониторингом свободного места и проверенным местом назначения резервных копий;
- корректное системное время и надёжное разрешение DNS;
- процедуру обновления ОС, которая не заменяет незаметно постоянные volumes;
- доступ к текущему подписанному релизу Gateway и службе лицензирования.

Не храните единственную копию backup или ключа шифрования на хосте Gateway. Резервная копия базы без соответствующего материала шифрования секретов не является полным комплектом восстановления.

## Для оператора: сетевой доступ

Публичной установке обычно нужен входящий HTTP/HTTPS для интерфейса и API. Управляемые Nodes подключаются через Relay, которому требуется доступный `9443/tcp`, если Nodes находятся вне локальной сети. По возможности ограничивайте административный доступ на сетевой границе, но не ставьте прокси или firewall в путь Relay, если он не поддерживает необходимые долгоживущие соединения.

Исходящий доступ зависит от включённых функций. Типичные назначения: identity providers, ACME- и DNS-провайдеры, системы контроля версий, container registries, службы релизов и лицензирования, email/webhook endpoints, SIEM receivers и настроенные AI providers. Для Build Workers может требоваться отдельная, более строгая политика egress.

Перед изменением firewall изучите [Порты и сеть](/ru/reference/ports-and-network/). Проверяйте путь с реального хоста и из того network namespace, который будет инициировать соединение: успешный запрос с ноутбука администратора не доказывает, что Gateway или Node доступен тот же endpoint.

## Роли Nodes и границы доверия

Выбирайте только нужные роли:

- **nginx node:** Ingress, материализация TLS, Pages, access/error logs и метрики трафика;
- **Docker node:** Containers, Deployments, Compose Projects, файлы, логи и состояние runtime;
- **database node:** управляемые экземпляры PostgreSQL, Redis или ClickHouse и их постоянное хранилище;
- **Build Worker:** изолированное выполнение BuildKit/containerd без передачи сокета Docker Engine;
- **monitoring node:** специализированный сбор мониторинга для поддерживаемых целей;
- **Relay Pool member:** дополнительная ёмкость и устойчивость плоскости данных Secure Link.

Разделение ролей — эксплуатационное решение и граница безопасности. Database Node требует политики хранения и backup, подходящей для stateful-сервисов. Build Worker обрабатывает управляемый репозиторием ввод сборки и не должен делить хост с посторонними workloads или многоразовыми инфраструктурными учётными данными. Считайте внешнюю VM или непривилегированный системный контейнер границей безопасности; внутренний sandbox сборки — дополнительная защита, а не единственная граница.

## DNS и сертификаты

Решите, будет ли Gateway управлять DNS через Cloudflare или записи останутся под внешним управлением. Для выпуска сертификата через HTTP-01 требуется публичный порт 80 на назначенном Ingress Node. Для DNS-01 нужна настроенная интеграция с минимальными правами на создание challenge records. Для загруженных сертификатов назначьте владельца renewal и контроля срока действия.

Для первоначального URL Gateway используйте hostname, уже покрытый доверенным сертификатом. Предупреждения браузера во время bootstrap подталкивают к небезопасным обходам и могут скрыть реальные проблемы прокси или hostname.

## Проверка готовности

До запуска установщика подтвердите всё перечисленное:

1. Канонический hostname разрешается в нужный endpoint.
2. Модель завершения TLS и владелец forwarded headers документированы.
3. Постоянное хранилище и внешнее место для backup подготовлены.
4. Firewall покрывает веб-приложение, Relay и необходимые исходящие службы.
5. Назначены первый администратор и второй владелец recovery-доступа.
6. Роли Nodes и изоляция хостов выбраны осознанно.
7. Зафиксированы требования к retention, аудиту, уведомлениям и SIEM.
8. Доступны необходимые права тарифного плана.

Если какое-либо решение неизвестно, остановитесь до подключения production workloads. Менять topology, DNS или аутентификацию значительно безопаснее до того, как от них начнут зависеть Nodes и интеграции.

Перед изменением firewall см. раздел [Порты и сеть](/ru/reference/ports-and-network/).
