Gateway — это infrastructure control plane: единая управляемая точка для публикации сервисов, эксплуатации распределённых Nodes, управления application runtimes и databases и сохранения видимой, атрибутируемой истории действий. Интерфейс организован вокруг эксплуатационных результатов, а не сырого списка серверов.

Для evaluator особенно важен ownership. Gateway координирует ресурсы, которыми управляет, но базовые hosts, networks, source repositories, DNS zones, backup destinations и external providers остаются ответственностью вашей организации. Здоровая оценка продукта должна показать обе стороны: удобное централизованное управление и явные границы, где решение всё ещё принадлежит человеку или внешней системе.

## Начните с Dashboard

Dashboard обобщает resource counts, health, recent activity, pinned resources и системные предупреждения, например недоступный Relay или проблему лицензии. Он отвечает на вопрос «требует ли что-то внимания?» и даёт путь к affected resource.

Это не универсальный observability screen. Подробные metrics и logs находятся на соответствующих Node, Route, workload, database, Pages Project или logging environment. Жёлтый indicator в navigation может означать предупреждение вне небольшого healthy subset, показанного на Dashboard, поэтому открывайте связанную деталь, а не считайте summary противоречивым.

**Цель оценки:** пользователь должен перейти от high-level warning к resource, operation или log с объяснением, не получая лишних административных прав.

## Ingress: публикация и защита traffic

Область Ingress разделяет три ответственности:

- **Domains** хранят hostnames и выбирают eligible Ingress Node.
- **SSL Certificates** централизуют lifecycle сертификатов и deployment status.
- **Routes** соединяют domains с upstream applications и применяют forwarding, TLS, maintenance, access и health policy.

Разделение делает изменения безопаснее. Application можно откатить без изменения DNS, а обновлённый сертификат — распространить без rebuild workload. Managed Docker upstreams могут использовать Secure Link, чтобы не публиковать обычный host port только ради ingress.

**Ownership:** network и DNS owners утверждают reachability; security owners — TLS и access rules; application owners — ожидаемый upstream и health response.

## Docker: эксплуатация application runtimes

Docker охватывает standalone Containers, blue/green Deployments, Compose Projects, images, volumes, networks, registries, Git builds и durable Tasks. Выбирайте resource model по ownership:

- **Container** — непосредственно управляемая одиночная workload;
- **Deployment** добавляет health-checked rollout и rollback;
- **Compose Project** владеет multi-service application, immutable revisions и дочерними services.

Gateway защищает эти границы. Compose-owned child containers не показываются как обычные standalone lifecycle targets, потому что их stop или recreate вне project создаст drift и ложное состояние. Долгие операции представлены как Tasks, чтобы cancellation, progress, failure и audit history сохранялись после reload страницы.

**Цель оценки:** развернуть безопасную тестовую workload, изучить logs и metrics, выполнить controlled update и убедиться, что UI показывает фактический runtime state, а не только запрошенную операцию.

## Databases: state без выдачи owner credentials

Раздел Databases хранит external connections PostgreSQL, Redis или ClickHouse и создаёт managed instances на database Nodes. Managed databases по умолчанию private. Application получает binding-specific identity вместо database owner credential, что ограничивает blast radius компрометации workload и позволяет независимо отозвать binding.

Database ownership отличается от application ownership. Удаление binding убирает доступ приложения; удаление managed database — destructive data operation, которая также удаляет managed storage. Backup, retention, capacity и recovery следует определить до создания production data.

**Цель оценки:** создать disposable database, привязать тестовую workload, проверить query, пересоздать workload и подтвердить сохранение binding без раскрытия owner credentials.

## Pages: публикация immutable static artifacts

Pages размещает static sites как immutable Deployments на Ingress Nodes. **Tag** — перемещаемый release pointer, а каждый Deployment остаётся неизменным. Route отправляет public domain на выбранный Tag. Это даёт простой rollback: вернуть Tag на known-good Deployment, а не изменять files на месте.

Projects принимают загруженные artifacts. Если тарифный план разрешает Git-source delivery, Gateway может собрать подключённый repository через isolated Build Worker и опубликовать approved artifact. Runtime configuration по дизайну public и никогда не должна содержать secrets.

Landing Good Gateway и этот documentation portal — примеры сайтов, которые можно обслуживать через Gateway Pages; продукт использует тот же delivery path, который документирует.

## Nodes: capabilities без смешивания trust domains

Nodes — зарегистрированные Linux-хосты с явными ролями Ingress, Docker, Databases, Build Worker, Monitoring или Relay. Они инициируют authenticated connections к Gateway и сообщают реальные version, capabilities и health. Enrollment использует one-time token и certificate pinning; долговременная связь — mutual TLS.

Поэтому Nodes list — не просто inventory. Он показывает, где находится capability и может ли Gateway сейчас на неё полагаться. Role selection должна следовать ownership и isolation host, а не удобству.

**Цель оценки:** зарегистрировать disposable Node, перезапустить daemon, подтвердить reconnection и проверить, что пользователь с resource-scoped access не может управлять посторонними Nodes.

## Logging, monitoring и operations

Gateway не предоставляет отдельное универсальное приложение «Observability». Monitoring и logs показываются в контексте Nodes, workloads, Routes, databases и Compose Projects. Structured Logging предоставляет environments, schemas, tokens, retention и optional SIEM delivery. Notifications, status pages, Tasks, recent activity и audit history рассчитаны на разные аудитории и не взаимозаменяемы.

Используйте metrics для понимания текущего поведения, logs для диагностики событий, Tasks для отслеживания операций, notifications для вызова responders, а audit records — для ответа на вопрос, кто и что изменил. Production alerting должен фокусироваться на customer impact и устойчивых state transitions, а не каждом внутреннем retry.

## Доступ и администрирование

Settings, users, groups, scopes, authentication methods, API tokens, OAuth clients, integrations, licensing, updates и housekeeping администрируются централизованно. Gateway поддерживает resource-scoped permissions: пользователь может получить доступ к одному Route, Node, workload или database, а не ко всей области продукта.

Profile показывает personal preferences, active authorizations и — в включённых средах — Inference usage. До приглашения большой команды создайте groups вокруг должностных обязанностей и сохраните отдельно контролируемый recovery path для system administration.

## AI и программное управление

AI Workspace предоставляет intent-driven interface для чтения документации, планирования и выполнения операций в пределах permissions и approval mode текущего пользователя. Он не создаёт отдельный authorization bypass. Operations Console, REST API, OAuth clients и MCP открывают те же product resources для deterministic или automated workflows.

Gateway Inference — отдельная data plane с выделенными `gwi_` tokens, providers, accounting и model access rules. Включение AI Workspace не выдаёт автоматически каждому пользователю доступ ко всем models или infrastructure actions.

## Практичная последовательность оценки

1. Изучите Dashboard и откройте реальное предупреждение resource или recent operation.
2. Зарегистрируйте disposable Node и проверьте recovery после restart.
3. Разверните тестовое приложение и изучите logs и metrics.
4. Опубликуйте его через Domain, certificate и Route.
5. Создайте least-privilege group для operator и подтвердите boundary.
6. Выполните rollback или maintenance без удаления resource.
7. Просмотрите созданные Tasks и audit history.

Эта последовательность демонстрирует основную ценность Gateway: единый governed workflow между инфраструктурными domains с сохранением явной ответственности за базовые системы и recovery.
