# Git-развёртывания Pages

Git-развёртывание Pages превращает одну выбранную ревизию репозитория в новый неизменяемый Deployment статического сайта. Источник Git и Build Worker создают артефакт; Pages Project владеет опубликованной историей развёртываний; Tags и Routes определяют, когда артефакт становится доступен пользователям.

## Перед началом

Подключите поддерживаемую интеграцию Git и выберите репозиторий и ветку, которые интеграции разрешено читать. Убедитесь, что выделенный Build Worker находится в сети, проект содержит правильное определение сборки, а необходимые Build Secrets с областью источника доступны. Build Secrets предназначены для изолированной границы сборки; конфигурация runtime публична и не должна содержать эти секреты.

Проверьте `package.json` репозитория, если он используется для обнаружения сборки, выберите подходящий package manager и команду сборки и убедитесь, что результат является артефактом статического сайта. Git-развёртывание не предоставляет через Pages runtime серверного приложения.

## Соберите Deployment

1. Выберите репозиторий, ветку и нужную ревизию для Pages Project.
2. Настройте обнаружение сборки, package manager, команду сборки и Build Secrets с областью источника.
3. Запустите сборку и следуйте за операцией на назначенном изолированном Build Worker.
4. Проверьте очищенный лог сборки, результат политики, ревизию источника и неизменяемый результат.
5. Создайте или выберите полученный Deployment, затем проверьте его до перемещения production Tag.

Сборка намеренно отделена от публикации. Завершённая сборка создаёт неизменяемый Deployment-кандидат; она не меняет пользовательский Tag или Route. Автоматическую сборку и автоматическое развёртывание следует считать независимыми настройками и включать автоматическое развёртывание только после понимания пути проверки, promotion и отката.

## Продвиньте и проверьте

Переместите нужный Tag на одобренный Deployment. Routes указывают на этот Tag, поэтому его перемещение является событием promotion. Проверьте DNS и TLS публичного домена, возвращаемый документ и статические assets, видимый клиенту `window.runtime.config` и состояние операций проекта. Используйте неизменяемый preview, если он настроен, чтобы проверить конкретный артефакт без перемещения публичного Tag.

Сохраняйте предыдущий заведомо исправный Deployment на время окна отката. Конфигурация runtime должна оставаться совместимой, пока один Tag может выбирать любой из релизов: её изменение может поменять поведение сайта без создания нового Deployment или изменения hashes артефакта.

## Неудачная сборка, отмена и откат

Неудачная или отменённая сборка не должна менять активный публичный релиз. Проверьте назначение worker и логи, чтобы отличить ошибки авторизации источника, зависимости, команды сборки, Build Secret, политики или результата артефакта. Исправьте причину и повторите попытку; каждая попытка создаёт новую операцию, не изменяя исторический результат.

Если продвинутый релиз вызвал инцидент, переместите Tag Route обратно на предыдущий проверенный Deployment. Затем проверьте ответ Route, assets, конфигурацию runtime и состояние приложения nginx. Не редактируйте и не заменяйте неисправный Deployment на месте: его неизменяемая запись важна для диагностики и свидетельств отката.

## Ручные релизы и очистка

Ручной релиз Pages следует той же модели promotion: создайте новый неизменяемый Deployment из подготовленного статического артефакта, проверьте его и перемещайте Tag только когда всё готово. История Git полезна для происхождения, но не обязательна, чтобы ручной артефакт участвовал в том же жизненном цикле Tag и Route.

При отключении источника Git решите, какие существующие Deployments всё ещё нужны для отката. Удаление источника останавливает будущие сборки из него, но автоматически не снимает публикацию существующего Tag и не удаляет развёрнутый артефакт. До удаления любого Deployment проверьте ссылки Tags и политику хранения.
