Поддержка источников Git связывает одобренную ревизию репозитория с неизменяемым артефактом сборки. Такой источник может поставлять Container Docker, Deployment или релиз Pages, но итоговая рабочая нагрузка всё равно следует жизненному циклу владеющего ресурса. Подключение источника само по себе не даёт права менять production Route или цель трафика.

## Решите, что разрешено автоматизации

Разделите три решения: кто может читать source, что считается одобренным artifact и может ли этот artifact deploy-иться автоматически. Такое разделение позволяет автоматизировать обычные релизы, не выдавая repository webhook неограниченные production-полномочия.

Владелец source контролирует доступ к repository и commit для сборки. Platform owner контролирует Build Worker, build policy, registry и deployment target. Service owner задаёт acceptance и rollback. Gateway связывает эти записи и сохраняет provenance от commit до digest, но успешная build остаётся только входом для релиза.

Используйте automatic build, когда каждое выбранное изменение source должно создавать artifact. Включайте automatic deploy только после проверки health gate и recovery path владеющего ресурса и только для branches, модель change control которых это допускает. Для более рискованных сервисов сохраняйте approval artifact и deployment отдельными человеческими решениями.

## Предварительные условия и владение

Используйте поддерживаемую разрешённую интеграцию источника и выдавайте только тот доступ к репозиторию, который нужен для сборки. Выберите точную ревизию ветки и убедитесь, что назначенный выделенный Build Worker находится в сети. Worker принимает одну сборку за раз, использует изолированное состояние BuildKit и containerd, применяет фиксированные ограничения ресурсов, запрещает небезопасные build entitlements и очищает кэш между заданиями.

Build Secrets ограничены источником и монтируются как секреты во время сборки. Не помещайте учётные данные в аргументы сборки, ссылки на image, URL репозитория, закоммиченную конфигурацию или логи. Build Worker владеет изоляцией выполнения; registry хранит созданный артефакт; целевой Docker Node позднее загружает и запускает этот артефакт.

## Соберите и проверьте артефакт

1. Подключите интеграцию и выберите репозиторий, ветку и нужную ревизию.
2. Настройте входные данные сборки и secrets, ограниченные источником.
3. Запустите сборку и следуйте за её Task от назначения worker до публикации артефакта.
4. Проверьте очищенные логи, результаты поиска уязвимостей, итог политики, исходный commit и неизменяемый digest артефакта.
5. Выберите одобренный digest в рабочем процессе владеющего Container, Deployment или Pages.

Автоматическая сборка и автоматическое развёртывание — независимые настройки. Оставляйте автоматическое развёртывание отключённым, пока не подтвердите путь проверки состояния и отката для этой рабочей нагрузки. Успешная сборка доказывает только существование артефакта; она не доказывает, что приложение корректно запускается на целевом Node.

## Обработка сбоев

Если сборка не может начаться, проверьте авторизацию источника, доступность worker, право по тарифному плану и состояние интеграции. Если ошибка произошла после запуска, используйте фазу и логи, чтобы отделить сбои зависимости, secret, политики, определения сборки или публикации артефакта. Исправьте источник или конфигурацию сборки и запустите новую сборку. Повторная попытка создаёт новую операцию и сохраняет прежнюю историю.

Когда worker или автоматизация источника недоступны, существующая история остаётся полезной для диагностики, но нельзя предполагать, что новые сборки выполняются. Не заменяйте отсутствующий неизменяемый артефакт изменяемым image tag; дождитесь проверенной сборки или используйте отдельно одобренный image.

## Очистка и откат

Удаление подключения источника блокирует будущую работу из источника, но автоматически не удаляет уже развёрнутый runtime или его артефакт. Перед отзывом подключения решите, какие артефакты всё ещё нужны для отката. Хранение артефактов определяется registry и историей активных, rollback-, выполняющихся, закреплённых и недавно успешных состояний владеющего ресурса.

## Критерии успеха

Приемлемая build идентифицирует repository и точный commit, завершается на одобренном worker, создаёт immutable digest, проходит настроенную vulnerability policy и показывает logs без secrets. Deployment acceptance выполняется отдельно: целевой ресурс должен pull-нуть digest, успешно запуститься, пройти health verification и обслужить ожидаемый client path.

Храните достаточно build- и artifact-history, чтобы объяснить, что запущено, и восстановить предыдущий known-good release. Mutable tag, успешный console log или зелёный build badge без digest недостаточны как production evidence.

## Операторские детали: isolation и диагностика

Build Workers — выделенные execution boundaries, потому что содержимое repository и build definitions могут исполнять код. Сужайте credentials worker, не размещайте рядом несвязанные чувствительные workloads и считайте build output недоверенным до завершения policy и provenance checks. Build Secrets должны монтироваться только в нужный шаг и не попадать в image layers.

Если build находится в queue, отделите нехватку capacity worker от ошибки source или policy. Если она запустилась и упала, определите фазу: source checkout, dependency resolution, Dockerfile или Compose build, vulnerability admission, registry publication или final acknowledgement. Сохраните ограниченный log и commit до повторной попытки. Retry должен создавать новую auditable attempt, а не перезаписывать failed record.
