# Обзор Docker

Gateway придаёт рабочим нагрузкам Docker долговечную продуктовую идентичность, а не считает запущенный контейнер всем приложением. Эта идентичность хранит конфигурацию, права доступа, историю жизненного цикла, связи и желаемое состояние, которое Gateway может восстановить после прерывания.

Выбирайте самый высокий уровень жизненного цикла, соответствующий приложению:

- **Container:** один runtime с прямым управлением, сфокусированной конфигурацией и жизненным циклом.
- **Deployment:** стабильная идентичность приложения с двумя runtime-слотами для сине-зелёных релизов с проверкой состояния и отката.
- **Compose Project:** обнаруженное внешнее приложение или управляемое Gateway одновузловое приложение с проверенной конфигурацией, неизменяемыми ревизиями, операциями жизненного цикла, логами, Routes и database bindings.
- **Git source:** входные данные доставки для Containers, Deployments и Pages. Это не отдельная сущность приложения.

## Границы владения

Gateway владеет метаданными и желаемым состоянием созданных или принятых им ресурсов. Целевой Docker daemon владеет процессом runtime, кэшем image, реализацией локального хранилища и подключением к сети. Поэтому управляемый ресурс может быть недоступен, пока его желаемое состояние остаётся записанным; восстановление начинается с возврата соединения daemon или Node, после чего Gateway выполняет реконсиляцию.

Некоторые объекты Docker принадлежат владельцу более высокого уровня. Слотами Deployment управляют через Deployment, а Containers с метками Compose группируются в контексте обнаруженного проекта. Не изменяйте дочерние ресурсы, управляемые владельцем, через автономный путь жизненного цикла: прямые изменения могут создать расхождение между состоянием работающего daemon и конфигурацией, записанной в Gateway.

Внутренние ресурсы, управляемые Gateway, могут включать labels, runtime-имена, networks, volumes, учётные данные, артефакты сборки и записи Tasks. Считайте их деталями реализации, если только действие Gateway явно их не показывает. Удаление или переименование таких ресурсов через инструменты Docker может нарушить реконсиляцию, маршрутизацию или будущий откат.

## Как выполняются операции жизненного цикла

Долгие изменения представлены Tasks или операциями. Операция записывает намерение, проходит этапы работы daemon и завершается результатом успеха или ошибки, который можно изучить позже. Запуск второго конфликтующего действия во время активной операции может быть отклонён или отложен; дождитесь текущей операции до повторной попытки.

Перед изменением рабочей нагрузки проверьте зависимые Routes, database bindings, гранты, подключённые volumes, настройки источника и политику перезапуска. Перед удалением решите, нужно ли сохранить её данные и публичные точки входа в другом месте. Успешная остановка runtime не равна завершённому удалению.

## Безопасная последовательность эксплуатации

1. Убедитесь, что выбранный Docker Node в сети и имеет требуемую capability runtime.
2. Перед редактированием конфигурации проверьте владельца ресурса и связанные ресурсы.
3. Выполните одно намеренное изменение жизненного цикла и следуйте за его Task до завершения.
4. Проверьте состояние, логи приложения и ожидаемый Route или приватное подключение.
5. Сохраняйте заведомо исправный image или предыдущий слот Deployment до окончания окна восстановления.

Если операция завершается ошибкой, используйте её диагностику, чтобы отличить ошибки image, конфигурации, storage, порта, прав и соединения Node. Исправьте указанное предварительное условие и повторите действие из Gateway. Не удаляйте принадлежащие Gateway Docker-объекты как универсальный шаг восстановления.
