Container — это вариант прямого управления одним Docker runtime. Gateway хранит его конфигурацию и связи доступа, а выбранный Docker daemon запускает и контролирует фактический процесс. Используйте Container, когда не нужны слоты сине-зелёного выпуска или владение многосервисным проектом.

## Когда Container — правильный владелец

Выбирайте Container для одного сервиса, restart, update и recovery которого можно управлять как единым runtime. Это подходит внутренним инструментам, агентам, stateless-сервисам и workloads с простой связью с persistent volume. Владелец приложения по-прежнему решает, безопасна ли замена процесса и требуют ли данные backup или maintenance window.

Выбирайте Deployment, если релиз нужно подготовить и проверить до переключения трафика с сохранением кандидата для отката. Выбирайте Compose, когда несколько сервисов, networks, variables и volumes должны меняться одной revision. Container намеренно остаётся прямой моделью: Gateway не придумывает вокруг него release strategy приложения.

Успех означает больше, чем состояние `running`. Ожидаемый health check должен проходить, приложение — слушать выбранный port, его Route или private connection — работать, а постоянные данные — оставаться подключёнными после recreate. Определите эти проверки до первого production update.

## Перед началом

Вам нужен доступ к целевому Docker Node и право создавать или изменять Container. Убедитесь, что image доступен из разрешённого registry, на Node достаточно ресурсов, а запрошенный runtime поддерживается. До выбора имени проверьте порты, Routes, database bindings, управляемые volumes и secrets: эти связи могут повлиять на последующее переименование, миграцию или удаление.

Новые host bind mounts отклоняются. Для новых постоянных данных используйте локальные volumes, которыми управляет Gateway. Устаревшие bind mounts могут сохраняться при обычном обновлении, но после удаления их нельзя снова добавить через Gateway.

Runtime **Default** доступен на поддерживаемых Docker Nodes. Защищённый runtime gVisor требует подтверждённой работоспособной capability и несовместим с GPU, devices, host bind mounts, миграцией и экспортом архива.

## Создайте и обновите Container

1. Выберите Docker Node и image, по возможности используя неизменяемый digest для production-рабочей нагрузки.
2. Задайте command, entrypoint, environment, зашифрованные secrets, labels, порты, restart policy, ограничения ресурсов, health checks и управляемые volumes.
3. Проверьте разрешённую конфигурацию и создайте Container.
4. Следуйте за Task создания, пока daemon не сообщит состояние runtime.
5. Проверьте состояние, логи и любой Route или приватное подключение к базе данных до отправки трафика приложения.

Используйте **Recreate**, когда изменение конфигурации runtime требует замены процесса. Gateway сохраняет стабильную идентичность ресурса и заново создаёт нужный runtime. Используйте **Duplicate**, когда нужен отдельный ресурс с независимыми правами доступа и историей жизненного цикла. Используйте **Rename** только после проверки зависимых Routes, binding и интеграций.

## Проверяйте и эксплуатируйте

Представление сведений — это эксплуатационная запись: проверьте желаемое и наблюдаемое состояние, результат проверки, идентичность image, последние Tasks и логи. Используйте console или доступ к файлам только в рамках выданных областей и не превращайте интерактивную console в обычный путь развёртывания.

После перезапуска или переподключения daemon Gateway должен выполнить реконсиляцию сохранённого желаемого состояния. Если Container запущен, но не обслуживает трафик, последовательно проверьте health check, порт прослушивания, цель Route, environment и лог приложения.

## Обработка сбоев и очистка

Сбой загрузки image, недоступные учётные данные registry, конфликт портов, некорректный mount, неподдерживаемая capability runtime или исчерпанные ресурсы Node должны быть исправлены до повторной попытки. История Task показывает остановившийся этап; повтор без изменения предварительного условия обычно приводит к тому же сбою.

Перед удалением проверьте Routes, database bindings, гранты, volumes, настройки источника и экспортированные данные. Удаление Container снимает права ресурса, поэтому последующий Container с тем же именем не наследует доступ. Удаление volume — отдельное разрушительное действие; сохраните или скопируйте постоянные данные перед удалением любого из ресурсов.

## Операторские детали: recreate и recovery

Изменение image, command, environment, mounts, runtime, ports, limits или restart behavior может требовать recreation. Recreation заменяет Docker runtime, сохраняя стабильную identity Container в Gateway и поддерживаемые связи. Текущие in-process sessions прерываются, поэтому планируйте окно или используйте Deployment, если перерыв недопустим.

Перед recreation запишите текущий image digest, health result, подключённые volumes, состояние Route и bindings и специфичное для приложения требование drain. После завершения Task сравните новый runtime с сохранённым desired state и проверьте реальный клиентский путь. Если startup не прошёл, верните прежнюю известную исправную конфигурацию или image и выполните recreate снова; не редактируйте неисправный Docker object вне Gateway.

Если Docker Node отключился во время операции, дождитесь свежего inventory после reconnect до повторной попытки. Хост мог завершить runtime action, не подтвердив его. Если Container отсутствует, но его desired state сохранён, используйте поддерживаемый reconcile или recreate. Удаление и повторное создание записи Gateway меняет ownership и grants и не должно быть первым способом восстановления.

Console и file access — инструменты инцидента и инспекции, а не замена воспроизводимой конфигурации. Изменения только внутри работающего container могут исчезнуть при следующем recreate; переносите их в image, managed configuration или persistent volume.
