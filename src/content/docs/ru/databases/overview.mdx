Gateway объединяет две разные модели баз данных в одной операционной поверхности: сохранённые внешние подключения и управляемые экземпляры баз данных. Различие заключается во владении. Внешнее подключение фиксирует доступ к сервису, который эксплуатируется в другом месте; управляемый экземпляр имеет контролируемый Gateway жизненный цикл на Node профиля Databases.

Выберите модель до подключения приложения. Используйте внешнее подключение, когда другая платформа или команда баз данных уже отвечает за доступность, резервные копии, обновления и сетевую политику. Используйте управляемый экземпляр, когда Gateway должен подготовить движок, ограничить локальный диск, предоставить состояние и операции жизненного цикла и создавать приватные привязки приложений. Переход между моделями является миграцией, а не переключателем метаданных.

| Вопрос | Внешнее подключение | Управляемый экземпляр |
| --- | --- | --- |
| Кто запускает и обновляет движок? | Внешний владелец базы данных | Gateway через Databases Node |
| Кто отвечает за backup и restore данных? | Внешний владелец базы данных | Ваша команда эксплуатации с подходящими движку инструментами |
| Как подключаются рабочие нагрузки Gateway? | Через настроенный путь внешнего подключения | По умолчанию через приватные привязки приложений |
| Может ли Gateway приостановить, изменить размер или удалить движок? | Нет | Да, в рамках управляемого жизненного цикла |

## Модель ресурсов

Управляемые экземпляры PostgreSQL, Redis и ClickHouse по умолчанию приватны. Gateway координирует конфигурацию движка, хранилище, учётные данные, состояние, логи, операции и привязки приложений. Выбранный Database Node запускает движок, а Gateway сохраняет желаемое состояние ресурса и его связи с рабочими нагрузками.

Внешнее подключение не передаёт Gateway владение базой данных. Gateway хранит конфигурацию подключения и учётные данные в зашифрованном виде с явным контролем прав, но доступность внешней базы данных, резервное копирование, политика доступа и жизненный цикл движка остаются ответственностью её оператора.

Рассматривайте сохранённые учётные данные как привилегированные инфраструктурные секреты. Разделяйте права просмотра, изменения, раскрытия и выполнения запросов, когда это допускает ролевая модель, и не используйте owner или superuser account, если достаточно более узкой service account. Удаление внешнего подключения удаляет сохранённое отношение Gateway, но не удаляет удалённую базу, её хранилище или пользователей.

## Приватный доступ по умолчанию

Используйте привязку приложения, когда управляемой рабочей нагрузке нужен доступ к управляемой базе данных. Привязка предоставляет отдельную идентичность движка с минимальными правами и обращается к базе данных через приватный listener, принадлежащий daemon. Listener создаётся непосредственно целевым Docker daemon в выделенной bridge network; отдельного сервиса на стороне привязки для эксплуатации нет.

Этот транспорт отличается от коннектора Secure Link между nginx и рабочей нагрузкой. Secure Link остаётся отдельным компонентом для собственных задач Ingress и Relay. Не воспринимайте сбой привязки как признак того, что компонент Secure Link следует удалить, пересоздать или настроить как транспорт базы данных.

Прямая публикация TCP — явная opt-in функция для внешних клиентов. Она не открывает firewall хоста автоматически и должна включаться только для определённого клиентского пути с подходящими учётными данными и доверием к сертификату. Публикация экземпляра не меняет приватную модель привязок, используемую рабочими нагрузками.

## Границы жизненного цикла и эксплуатации

Страница сведений о базе данных объединяет состояние, метрики, настройки движка, учётные данные, сертификаты, изменение размера, pause/unpause, restart, логи и доступные функции Explorer или Console. Доступные действия зависят от движка, соединения с Node, состояния экземпляра и выданных вам прав.

Pause сохраняет данные, намеренно отключая вычисления движка. Приостановленный экземпляр не предоставляет обычные данные состояния, метрики, Explorer или Console, пока не будет возобновлён. Restart полезен как контролируемая эксплуатационная операция; он не исправляет нерешённые проблемы хранилища, аутентификации или Node.

## Базовая проверка готовности

До передачи базы команде приложения проверьте всю границу владения:

1. Выбранный Database Node находится в сети и сообщает о поддерживаемых возможностях хранилища.
2. Управляемый экземпляр имеет статус **Ready**, либо внешний endpoint доступен с нужной TLS-политикой.
3. Владение резервными копиями, срок хранения и свидетельства восстановления документированы вне самого экземпляра.
4. Приложение использует идентичность отдельной привязки или другую account с минимальными правами, а не owner credential.
5. Мониторинг собирается без необходимости держать страницу сведений открытой.
6. Контролируемый restart или reconnect доказывает ожидаемое восстановление клиента.

Один зелёный badge движка не доказывает сквозную доступность. Подтвердите реальный запрос приложения, ожидаемую границу прав и отсутствие учётных данных в исходном коде, логах, результатах Tasks и публичной конфигурации runtime.

## Доступность и ограничения

Управляемые экземпляры являются single-node ресурсами. Gateway сохраняет желаемое состояние и координирует восстановление, но не превращает один процесс базы данных в multi-node кластер высокой доступности. Планируйте резервирование хостов, репликацию данных, внешние резервные копии и время восстановления согласно критичности базы.

Резервная копия конфигурации Gateway не заменяет backup данных базы. Удаление управляемой базы, в свою очередь, должно удалять её управляемое хранилище; до подтверждения удаления используйте проверенную резервную копию или цель миграции.
