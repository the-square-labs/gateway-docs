Привязка приложения предоставляет одному Container, Deployment или подходящему service рабочей нагрузки приватный доступ к одной управляемой базе данных. Gateway создаёт для привязки отдельного пользователя или роль движка и выдаёт только те права базы данных, которые ей необходимы. Идентичность движка принадлежит привязке, а не временному процессу рабочей нагрузки.

## Модель транспорта и владения

Для каждой привязки целевой Docker daemon владеет TCP listener в выделенной bridge network. Gateway выполняет реконсиляцию этого listener как части желаемого состояния привязки. Поэтому приватный endpoint остаётся связанным с окружением рабочей нагрузки, а не реализуется отдельным процессом для каждой привязки.

Listener daemon и идентичность движка привязки — отдельные, но согласованные записи. У каждой привязки есть собственный principal базы данных, поэтому ротация учётных данных, удаление или изменение прав одной рабочей нагрузки не меняет незаметно доступ другой. Пересоздание связанной рабочей нагрузки сохраняет отношение привязки и её отдельную идентичность движка; Gateway снова реконсилирует listener и внедряет актуальные настройки подключения.

Коннектор Secure Link между nginx и рабочей нагрузкой — отдельный реальный компонент. Он выполняет свою задачу Ingress и Relay и не является транспортной реализацией управляемых привязок баз данных. Диагностируйте состояние listener привязки и готовность базы данных независимо от состояния Secure Link, если только зафиксированная операция явно не указывает на проблему Ingress или Relay.

## Создайте привязку

Перед созданием привязки убедитесь, что управляемая база данных имеет статус **Ready**, целевой Docker Node находится в сети, рабочая нагрузка подходит для привязки, а у вас есть доступ к обоим ресурсам. Проверьте необходимые права базы данных или роли и убедитесь, что рабочая нагрузка может использовать переданные настройки подключения, не помещая их в систему контроля версий.

1. Выберите управляемую базу данных и целевую рабочую нагрузку.
2. Выберите необходимый доступ к базе данных с минимальными правами.
3. Создайте привязку и дождитесь, пока Gateway подготовит её идентичность движка и реконсилирует listener, принадлежащий daemon.
4. Применяйте или пересоздавайте рабочую нагрузку только когда этого требует изменение её конфигурации.
5. Выполните реальный запрос приложения, затем проверьте телеметрию привязки и логи рабочей нагрузки и базы данных.

Используйте приватные привязки для доступа рабочих нагрузок, даже если для внешнего клиента включена прямая публикация TCP. Публикация включается явно и не заменяет изоляцию привязок.

## Реконсиляция и обработка сбоев

Желаемое состояние привязки надёжно сохраняется при пересоздании рабочей нагрузки, перезапуске Docker daemon, переподключении Node и перезапуске Relay. Реконсиляция восстанавливает listener, принадлежащий daemon, и подтверждает идентичность движка, не создавая новую идентичность для каждого временного runtime. Так Gateway избегает осиротевших ролей при обычных перезапусках и пересозданиях.

При сбое привязки диагностируйте в таком порядке: готовность управляемой базы данных; целевой Database Node; целевой Docker Node; желаемое состояние привязки; состояние listener daemon; идентичность и права движка; затем конфигурацию приложения. До повторной попытки изучите операцию и телеметрию привязки. Не удаляйте роль движка, bridge network или listener вручную как универсальный способ ремонта: это может рассинхронизировать долговечную запись с базой данных и daemon.

## Удаление и восстановление

Удаляйте привязку через Gateway, когда рабочей нагрузке больше не нужен доступ. Gateway удаляет отношение listener и выводит идентичность движка привязки из эксплуатации в рамках одного зафиксированного жизненного цикла, поэтому обычное удаление не оставляет неиспользуемые идентичности. По возможности удаляйте привязку до базы данных или рабочей нагрузки, затем убедитесь, что очистка listener, телеметрии и principal движка завершена.

Если удаление прервано, оставьте долговечную запись привязки на месте и используйте состояние её операции для восстановления. Ручное удаление роли — исключительная процедура восстановления, поскольку оно может привести к сбою будущей реконсиляции; применяйте его только по явному согласованному плану восстановления.
