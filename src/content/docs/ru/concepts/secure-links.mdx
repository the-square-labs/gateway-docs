Secure Links соединяют поддерживаемые управляемые ресурсы Gateway, не превращая назначение в обычный публичный endpoint.

Термин описывает узкие приватные подключения с долговечным владением Gateway. Он не означает, что каждый приватный путь использует один runtime-компонент. Ingress upstream links и привязки управляемых баз данных имеют разных владельцев, учётные данные, записи жизненного цикла и диагностические сигналы.

## Предварительные условия и граница доверия

Обе стороны должны быть поддерживаемыми управляемыми ресурсами Gateway со стабильными идентичностями, а владеющие Nodes — находиться в сети и иметь совместимые capabilities. Relay должен быть исправен и доступен участвующим Nodes. Вызывающей стороне нужны права на чтение целевого ресурса и изменение ресурса, владеющего связью.

Выбирайте service или порт приложения, на котором действительно слушает процесс. Публиковать порт хоста только ради приватной связи не нужно, а открытие порта не исправляет неисправный приватный путь. Gateway не создаёт правила firewall хоста и не делает произвольные сети доступными.

## Database bindings

Managed database binding соединяет один подходящий Container, Deployment или Compose service с одной управляемой базой данных. Gateway создаёт отдельного пользователя или роль движка для привязки и выдаёт только необходимые права базы данных. Рабочей нагрузке передаются данные подключения конкретной привязки; учётные данные владельца базы не раскрываются.

Целевой Docker daemon владеет TCP listener в выделенной приватной bridge network и реконсилирует его как часть желаемого состояния привязки. Отдельного Container-коннектора базы данных для каждой привязки не существует: его нельзя перезапустить, проверить или заменить. Listener и идентичность движка — отдельные, но согласованные записи, поэтому ротация учётных данных, изменение прав или удаление одной рабочей нагрузки не меняет незаметно другую привязку.

Пересоздание рабочей нагрузки сохраняет привязку, поскольку авторизация следует стабильной идентичности Gateway, а не временному ID Container. Gateway снова реконсилирует listener и внедряет актуальные настройки подключения. Удаление привязки снимает связь listener и выводит идентичность движка из эксплуатации в рамках одного зафиксированного жизненного цикла; обычный путь не должен оставлять осиротевшие роли или пользователей.

При сбое привязки базы данных проверьте управляемую базу и Database Node, затем целевой Docker Node и рабочую нагрузку, желаемое состояние привязки, listener daemon, идентичность и права движка и только потом конфигурацию приложения. Не удаляйте роль, bridge network или listener вручную как универсальный ремонт. Это может превратить восстанавливаемое расхождение в осиротевшую идентичность или сбой будущей реконсиляции.

## Ingress upstream links

Routes и Additional Routes могут направлять трафик к поддерживаемым Docker-ресурсам через Secure Link. Gateway проверяет выбранный ресурс и порт приложения, создаёт связь и реконсилирует принадлежащий Gateway коннектор через Relay. Коннектор трафика nginx-to-workload является реальным runtime-компонентом, но остаётся вне обычных пользовательских API жизненного цикла.

Связь, созданная управляемым Route, принадлежит этому Route. Она видна для диагностики, но не может быть удалена независимо; отключение Route сохраняет его конфигурацию и связь, а удаление Route выводит принадлежащую связь из эксплуатации после реконсиляции. Перезапуск или пересоздание рабочей нагрузки сохраняет link, потому что Route указывает на стабильный ресурс Gateway. Promotion Deployment и смена ревизии Compose разрешают активный runtime за той же идентичностью верхнего уровня.

Расширенные конфигурации nginx могут использовать отдельно управляемые дополнительные привязки с собственным жизненным циклом. Не путайте их с привязками, принадлежащими Route. Перед удалением пользовательской привязки определите все конфигурации, которые на неё ссылаются.

## Обычный процесс и проверка

Для Ingress upstream выберите управляемую цель в редакторе Route или Additional Route, укажите service или порт приложения и протокол, сохраните и дождитесь реконсиляции Secure Link и валидации конфигурации nginx. Затем проверьте идентичность цели, состояние коннектора, health Route и реальный внешний запрос.

Для управляемой базы данных создайте привязку между подходящей рабочей нагрузкой и базой, выберите доступ с минимальными правами, дождитесь идентичности движка и listener daemon, при необходимости примените конфигурацию рабочей нагрузки и выполните реальный запрос приложения. Проверьте телеметрию привязки и логи рабочей нагрузки и базы данных.

Проверка должна доказывать работу нужного пути, а не только существование записи. Для Ingress проверяйте доступность Relay, соединения обоих Nodes, задержку настройки, активные потоки, пропускную способность, состояние завершения, отклонения admission, логи nginx и поведение приложения. Для database bindings проверяйте готовность базы, реконсиляцию listener, состояние principal движка, соединение приложения и актуальную конфигурацию рабочей нагрузки.

## Что Secure Links не делают

- Это не универсальный VPN и не overlay-сеть.
- Они не обеспечивают произвольную переадресацию TCP или SSH.
- Они не открывают firewall хоста автоматически.
- Они не отменяют необходимость аутентификации на уровне приложения, если её требует протокол назначения.

Они также не передают владение целевым ресурсом, не делают неподдерживаемые рабочие нагрузки переносимыми и не авторизуют пользователя без доступа к обеим сторонам. Secure Link не является основанием открывать управляющие интерфейсы daemon, owner-порты базы данных или внутренние учётные данные коннектора.

## Сбой и безопасное восстановление

Если Ingress Route сохраняется, но трафик не проходит, проверьте включение Route и обслуживание, ревизию nginx, Relay, соединения Ingress и Docker Nodes, runtime и порт цели, admission коннектора, затем логи приложения и поведение протокола. Не публикуйте внутренний порт рабочей нагрузки как недокументированный обход.

После сбоя Node или Relay восстановите соединение и дождитесь свежих capabilities и реконсиляции желаемого состояния до замены идентичностей. Сохраняйте историю операций и request IDs. Если удаление прервано, оставьте долговечную запись владельца или привязки, чтобы Gateway мог завершить очистку. Ручное удаление принадлежащих Gateway коннекторов, сетей, listeners или principals движка — исключительная согласованная процедура восстановления, а не первый ответ.
