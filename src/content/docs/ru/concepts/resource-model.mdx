Ресурсы Gateway имеют стабильные идентичности, отдельные от изменяемых runtime-имён или идентификаторов контейнеров.

## Стабильные идентичности

Права, привязки, настройки источника, конфигурация health, история операций и состояние миграции привязаны к идентичности ресурса Gateway. Runtime-имена, IDs процессов и Containers, IP-адреса и размещение могут меняться без создания нового продуктового ресурса. Это позволяет Gateway пересоздавать или перемещать подходящие runtime-объекты, сохраняя намеренно настроенные оператором связи.

Пересоздание управляемой рабочей нагрузки сохраняет её идентичность Gateway, а значит и допустимые связи Route, привязок, грантов и источника. Дублирование создаёт отдельный ресурс с отдельными правами и историей жизненного цикла. Явное удаление снимает гранты, принадлежащие удалённому ресурсу, поэтому последующий ресурс с тем же отображаемым именем не получает полномочия случайно.

Используйте стабильные IDs ресурсов и операций для сопоставления ответов API, Tasks, событий, логов и записей аудита. Имена предназначены для операторов и могут меняться или совпадать на разных Nodes или в разных папках. Совпадения имени недостаточно, чтобы считать новый runtime-объект ресурсом, которым Gateway управлял ранее.

## Границы владения

- Compose Project владеет своими service-контейнерами, именованными volumes и сетями, не отмеченными как external.
- Сине-зелёный Deployment владеет обоими runtime-слотами и состоянием rollout.
- Управляемая база данных владеет своим database Container и identity владельца engine.
- Database binding владеет отдельной application identity с минимальными правами.
- Route или Additional Route может владеть своим Secure Link binding.
- Внутренние Containers, принадлежащие Gateway, недоступны API жизненного цикла пользователя.

Эти границы не позволяют API нижнего уровня обходить жизненный цикл верхнего уровня, создавшего ресурс. Дочерний объект может быть виден для диагностики, не становясь независимо изменяемым. Например, слоты Deployment проверяются через Deployment, services Compose — через Compose Project, а принадлежащий Route Secure Link — через создавший его Route.

Владение не распространяется автоматически на используемые зависимости. Route, использующий переиспользуемый сертификат или Access List, не владеет ими и не удаляет их. Рабочая нагрузка, размещённая на Node, не владеет этим Node. Pages Route указывает на Tag, но не владеет неизменяемым Deployment, выбранным этим Tag. Перед удалением или миграцией проверяйте как принадлежащих дочерних объектов, так и используемые зависимости: правила их очистки различаются.

Gateway также создаёт внутренние runtime-объекты для реализации продуктового поведения. Их labels, runtime-имена, сети, volumes, учётные данные, коннекторы и записи Tasks являются деталями реализации, если поддерживаемое действие не открывает их явно. Прямое удаление или переименование через Docker-инструменты хоста может нарушить реконсиляцию, маршрутизацию, приватное подключение или откат.

## Желаемое, сообщённое и runtime-состояние

Продуктовый ресурс хранит долговечное желаемое состояние в Gateway. Владеющий daemon сообщает инвентарь, capabilities, health и результаты операций. Runtime хоста содержит фактический процесс, конфигурацию, хранилище и сетевые подключения. Во время операции, перезапуска, разрыва соединения или сбоя эти представления могут временно расходиться.

Успешное сохранение означает принятие желаемого состояния, а не обязательное применение владельцем. Следуйте за долговечной Task и дождитесь свежего сообщённого состояния. Если Node отключён, Gateway может показывать очищенные данные последнего известного состояния, но блокирует мутации, требующие актуального владения или capability. Восстановите владельца и дайте пройти реконсиляции, прежде чем решать, что отсутствующий runtime-объект нужно пересоздать вручную.

## Папки и навигация

Папки организуют поддерживаемые ресурсы и могут участвовать в ограничении доступа. Они не меняют runtime-сеть, размещение или владение жизненным циклом. Перемещение или группировка ресурса в навигации не перемещает его runtime и не передаёт связанные зависимости.

Результаты поиска и command palette ведут на каноническую страницу ресурса Gateway, а не на дочерние объекты реализации. Так действия, история аудита, связанные ресурсы и средства восстановления остаются привязанными к стабильной идентичности, владеющей жизненным циклом.

## Внешние ресурсы

Созданные извне Compose Projects можно обнаруживать по каноническим Docker labels. Gateway может показывать их services, состояние, health, логи и инвентарь, но внешние проекты остаются доступными только для чтения, пока оператор явно не примет их во владение с полной YAML-конфигурацией и необходимыми правами. Adoption передаёт последующее управление Gateway только после валидации и подготовки неизменяемой ревизии; Gateway не доверяет пути хоста из label как исходной конфигурации.

Внешними базами данных по-прежнему управляет оператор. Gateway хранит их настройки подключения в зашифрованном виде, проверяет соединение и может предоставлять разрешённые инструменты, но не владеет обновлениями движка, хранилищем, резервным копированием, доступностью или удалением. Аналогично глобальные Docker images и намеренно external или общие ресурсы Compose остаются вне очистки дочерних объектов проекта.

## Безопасные изменения и удаление

Перед изменением ресурса определите его владельца, принадлежащие дочерние объекты, используемые зависимости, активную операцию, кандидата для отката и постоянные данные. Выполняйте одно изменение жизненного цикла через владельца самого высокого уровня и проверяйте итоговое состояние, связи и сообщённый статус. Не смешивайте прямые изменения хоста с активной операцией Gateway.

Удаление не является простым обратным созданием. Оно может снять гранты, удалить идентичности движка, принадлежащие Route связи, историю ревизий или слоты отката, намеренно сохраняя переиспользуемые сертификаты, Access Lists, внешние ресурсы или persistent volumes. Прочитайте подтверждение, отсоедините или перенесите зависимости, сохраните нужные данные и проследите Task удаления до очистки. Если очистка прервана, сохраните запись Gateway и используйте состояние операции для восстановления, а не удаляйте дочерние объекты принудительно.
