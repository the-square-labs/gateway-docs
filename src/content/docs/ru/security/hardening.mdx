# Чек-лист усиления защиты

- Поддерживайте хосты Gateway и daemon обновлёнными и по возможности выделенными под свои роли.
- Ограничьте PostgreSQL и Redis приватной сетью приложения.
- Открывайте только порты HTTPS и Relay, необходимые развёртыванию.
- Требуйте MFA от администраторов и минимизируйте состав администраторов.
- Храните master keys и резервные копии вне хоста Gateway.
- Используйте service credentials с областью ресурсов и короткими интервалами ротации.
- Предпочитайте неизменяемые image digests и выделенные Build Workers.
- Запрещайте host bind mounts и privileged/device access, если их не требует явный поддерживаемый процесс.
- Сохраняйте управляемые базы данных приватными и используйте идентичности привязок.
- Проверяйте продление сертификатов и сохраняйте системную PKI для внутреннего транспорта.
- При необходимости отправляйте события аудита в независимо контролируемый SIEM.
- Регулярно проверяйте интеграции источников, учётные данные registry, OAuth clients, токены и активные сеансы.
- Удаляйте временное обслуживание, debug-экспозицию и ручные изменения хоста после инцидентов.

Не публикуйте screenshots, support bundles или логи до маскирования секретов, внутренних адресов, имён клиентов и URL репозиториев.

## Плоскость управления

- Запускайте Gateway на выделенной VM или хосте и ограничивайте прямой shell- и Docker-доступ.
- Держите PostgreSQL, Redis, internal gRPC и inference core в приватных сетях.
- Защищайте `.env`, ключи шифрования, ключи PKI, загруженные артефакты и идентичность Relay строгими правами и резервными копиями.
- Используйте HTTPS на каноническом публичном URL и проверяйте поведение cookie, WebSocket, OAuth и proxy.
- Отключайте неиспользуемые методы аутентификации и интеграции.

## Управляемые Nodes

- Используйте одну идентичность регистрации на каждую роль хоста и никогда не копируйте сертификаты daemon между хостами.
- По возможности ограничивайте исходящие destinations Gateway/Relay и необходимыми providers.
- Защищайте systemd units, конфигурацию, trust anchors обновлений, runtime sockets и локальное хранилище.
- Изолируйте роли Ingress, Build Worker, Database и Relay согласно их риску.
- Оповещайте об устаревшем last-seen, деградации capabilities, давлении диска и несовместимости обновлений.

## Рабочие нагрузки и сборки

- Предпочитайте images, закреплённые по digest, и проверяйте источник, логи сборки, политику уязвимостей и границы происхождения.
- Запускайте Git-сборки только на выделенных Build Workers.
- Используйте управляемые volumes вместо host bind mounts.
- Не выдавайте privileged mode, произвольные devices, host networking или доступ к файловой системе хоста без явного поддерживаемого требования.
- Храните runtime и Build Secrets через отдельные зашифрованные пути.

## Данные и приватные подключения

- По умолчанию не публикуйте управляемые базы данных.
- Используйте одну идентичность привязки на каждое отношение приложения и проверяйте, что учётные данные владельца никогда не попадают в конфигурацию рабочей нагрузки.
- Защищайте принадлежащие Gateway сети привязок и принадлежащие daemon listeners от пользовательских операций жизненного цикла.
- Резервируйте данные приложений через engine-native процедуры и проверяйте восстановление независимо от восстановления Gateway.
- Сохраняйте прямой TLS базы данных включённым, если не документировано намеренное исключение приватной сети.

## Операционная уверенность

По установленному расписанию проверяйте состав администраторов, области групп, токены, OAuth clients, интеграции источников, DNS-коннекторы, учётные данные SMTP, destinations SIEM и активные сеансы. Проверяйте пути отказа через идентичности без административных прав.

Проводите учения по инцидентам, восстановлению, обновлениям, failover Relay, перезапуску Nodes, пересозданию рабочих нагрузок и восстановлению привязок баз данных. Удаляйте временный debug-доступ и документируйте каждое принятое исключение с владельцем и сроком.
