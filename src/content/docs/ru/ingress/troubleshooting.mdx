Цель инцидента — восстановить публичный сервис, не уничтожив состояние, объясняющее сбой. Ingress пересекает несколько границ ownership: DNS, сеть, сертификат, конфигурацию nginx, policy Route, приватный transport и application runtime. Одновременное изменение нескольких уровней обычно увеличивает outage.

Назначьте одного incident owner, зафиксируйте последнее known-good change и проверяйте снаружи внутрь. Успех означает восстановленное внешнее поведение, совпадение desired и reported state Gateway и запись неисправного уровня и recovery action, достаточную для предотвращения повторения.

Проверяйте уровни в таком порядке, чтобы не изменять не тот слой:

1. **DNS:** разрешите hostname из внешнего клиента и убедитесь, что он указывает на назначенный Ingress Node.
2. **Network:** подтвердите доступность публичных 80/443 и правила firewall хоста.
3. **TLS:** проверьте hostname сертификата, цепочку, срок действия и состояние распространения.
4. **nginx config:** убедитесь, что последняя ревизия применена и валидация конфигурации завершилась успешно.
5. **Route health:** проверьте ожидаемые статус/тело ответа и состояние обслуживания.
6. **Upstream:** проверьте приложение с Node nginx или состояние Secure Link.
7. **Logs:** сопоставьте access/error-логи nginx с логами рабочей нагрузки и идентификаторами запросов.

Распространённые ошибки: Domain и Route размещены на разных Nodes, после миграции остался устаревший внешний DNS, HTTP-01 используется на Node без публичного порта 80, приложение WebSocket работает без пересылки WebSocket, либо выбран порт рабочей нагрузки, который фактически не опубликован и не подключён.

## Таблица симптомов

| Симптом | Наиболее вероятный уровень | Первое свидетельство |
| --- | --- | --- |
| Hostname не разрешается | DNS | Внешний lookup `A`/`AAAA` и размещение Domain |
| Тайм-аут соединения | сеть | Публичный адрес, firewall, порты 80/443, доступность Node |
| Предупреждение о сертификате | TLS | Hostname сертификата, цепочка, срок действия и назначенный Route |
| Немедленный `404` | сопоставление Route | Hostname, префикс пути, состояние включения, raw config |
| Управляемый `503` | обслуживание или неисправный upstream | Состояние обслуживания и история состояния |
| `502`/`504` | транспорт upstream | Secure Link, целевой порт, состояние рабочей нагрузки, настройки timeout |
| WebSocket отключается | пересылка протокола | Опция WebSocket, путь приложения, тайм-ауты proxy/read |
| Изменения не появляются | применение/реконсиляция | Состояние Task, ревизия nginx, соединение Node, ошибка валидации |

## Соберите свидетельства до изменения состояния

Зафиксируйте неисправный hostname, path, время, класс IP клиента, ожидаемый и фактический ответ, назначенный Node, ID Route, ID последнего Task и соответствующий request ID. Сохраните ошибку валидации сгенерированной конфигурации и ограниченный объём логов до повторной попытки; повторные изменения могут стереть самые полезные свидетельства.

Сравните три представления:

1. желаемое состояние Gateway в сведениях Route и Domain;
2. последнее подтверждённое состояние от Node nginx;
3. внешнее наблюдаемое поведение DNS, TLS и HTTP.

Несовпадение между этими представлениями показывает, связана ли проблема с состоянием плоскости управления, применением на Node или внешней инфраструктурой.

## Безопасное восстановление

- Исправляйте DNS только после подтверждения нужного размещения Node.
- Исправляйте назначение сертификата, а не отключайте TLS глобально.
- Сначала устраните ошибку валидации конфигурации и только потом принудительно запускайте новое применение.
- Используйте режим обслуживания, если приложение должно оставаться недоступным во время ремонта.
- Повторяйте реконсиляцию только после восстановления зависимости, вызвавшей сбой.
- Откатывайте приложение или конфигурацию Route, если доступна заведомо исправная ревизия.

Не удаляйте и не создавайте заново Domain, сертификат или Route в качестве первого ответа. Это уничтожает историю связей и может вызвать второй сбой.

## Проверка восстановления

Выполните проверку из внешнего клиента, затем подтвердите канонический hostname, цепочку сертификата, код ответа, тело, перенаправления, WebSockets, историю состояния и логи nginx. Закрывайте инцидент только когда публичное поведение и состояние Gateway совпадают.

## Откат по неисправному уровню

Откат должен отменять минимальное изменение, вызвавшее outage. Для DNS восстановите записанные адреса с учётом кешей resolver. Для TLS верните прежнее валидное назначение сертификата, не отключая HTTPS. Для конфигурации nginx восстановите последние заведомо исправные управляемые настройки и дождитесь подтверждения. При регрессии приложения откатывайте владеющий Deployment или Compose revision, а не переписывайте Route вокруг сломанного релиза.

Сбои Secure Link требуют восстановления Relay, соединения Nodes или целевого runtime; изменения DNS и сертификата их не исправят. Ошибки access policy требуют вернуть прежний Access List или интерпретацию trusted proxy, а не открыть порт workload. Maintenance mode полезен во время ремонта: он сохраняет явный hostname и TLS-путь, но не допускает случайный трафик к частично восстановленному приложению.

## Данные для эскалации

Если первая попытка восстановления не объяснила сбой, перед эскалацией соберите ограниченный пакет данных:

- идентификаторы Domain и Route, назначенный Ingress Node и последнюю подтверждённую ревизию config;
- внешние DNS-ответы и сведения о TLS-сертификате, наблюдавшиеся во время инцидента;
- историю health Route и точные path, method, status и timestamp сбоя;
- связанные записи nginx access/error и операцию владеющего workload или Secure Link;
- версии Nodes и Relay, состояние соединения и последнее сообщение failed Task;
- последнюю заведомо исправную ревизию приложения, Route и DNS.

Удалите credentials, cookies, authorization headers, private keys и чувствительные query values. Цель — сохранить причинность, не превращая запись инцидента в хранилище секретов.
