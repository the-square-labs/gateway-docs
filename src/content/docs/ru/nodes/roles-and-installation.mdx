Роли Nodes разделяют эксплуатационные полномочия. Выбранная при enrollment роль определяет, какими ресурсами может управлять хост, какой software profile устанавливается и какие сбои способны повлиять на бизнес. Выбирайте роль по ответственности, а не по пакетам, которые случайно уже установлены на машине.

Platform lead должен до enrollment утвердить роль, ownership хоста, failure domain, чувствительность данных и владельца recovery. Успех означает, что одна постоянная identity Node установлена на нужном хосте, сообщает только ожидаемые capabilities и проходит малорисковую профильную acceptance-проверку до назначения production-ресурсов.

## Операторские детали: prerequisites профиля

Используйте сгенерированную команду установщика из потока создания Node. Она содержит ограниченные данные регистрации и зафиксированную идентичность Gateway.

- **nginx:** требует nginx, публичных портов Ingress, где это применимо, валидации конфигурации и доступа к логам.
- **Docker:** требует поддерживаемый Docker Engine и права на настроенные операции runtime.
- **database:** требует выделенного хранилища и средств kernel/storage, описанных установщиком.
- **builder:** требует выделенной ёмкости BuildKit/containerd и не должен иметь сокет Docker Engine.
- **monitoring:** предоставляет поддерживаемый сбор данных мониторинга.
- **Relay supervisor/worker:** расширяет ёмкость и устойчивость Relay с явным размещением.

После установки проверяйте передаваемый отчёт о возможностях, а не предполагайте поддержку по наличию пакетов на хосте. Функции GPU, Secure Runtime, builder, storage и migration зависят от сообщённых работоспособных возможностей.

## Выберите роль

- **Ingress:** завершает TLS и обслуживает публичные Domains и Routes. Ему нужны валидация конфигурации nginx, хранилище сертификатов, логи и, где применимо, публичные порты.
- **Docker:** управляет обычными рабочими нагрузками приложения и ресурсами Docker. Ему нужны поддерживаемый Docker Engine и права, необходимые выбранным функциям runtime.
- **Build Worker:** запускает Git-сборки в изолированных службах BuildKit/containerd. Он должен быть выделен под сборки и не должен открывать обычный сокет Docker Engine профилю builder.
- **Databases:** запускает управляемые PostgreSQL, Redis и ClickHouse с выделенной подготовкой storage и ограниченным профилем Docker daemon.
- **Monitoring:** собирает поддерживаемое состояние и метрики хоста, не получая прав на жизненный цикл рабочих нагрузок.
- **Relay:** устанавливает supervisor Relay, объявляет доступный адрес и присоединяется к Relay Pool Secure Link.

## Стандартный поток регистрации

1. Откройте **Nodes** и выберите **Add Node**.
2. Выберите нужный Node Type и прочитайте его описание.
3. Введите стабильное имя, понятное оператору.
4. Для Relay введите адрес, который участвующие Nodes могут достичь по TCP `9443`.
5. Создайте ожидающий Node.
6. Скопируйте сгенерированную одноразовую команду установки.
7. Выполните команду на нужном Linux-хосте.
8. Оставьте диалог результата открытым, пока демон устанавливается и регистрируется; он закроется автоматически, когда именно этот Node перейдёт в состояние online.
9. Откройте сведения о Node и проверьте роль, hostname, версию, возможности, метрики и service addresses.

Действие **Add relay node** в настройках Relay открывает тот же поток регистрации с заранее выбранным и заблокированным Relay. Участники Relay отображаются как готовая ёмкость пула только после успешной регистрации и передачи состояния.

## Подготовка хоста

Используйте выделенный хост или VM, когда роль владеет сильной границей доверия. До запуска установщика проверьте DNS, системное время, исходящую доступность Relay, требования к пакетам и runtime, постоянное хранилище и наличие systemd. Не переносите команду установщика между ожидающими записями Node.

Для database Nodes требуется предварительная проверка storage от установщика. Build Workers требуют выделенных вычислительных ресурсов и storage. Relay Nodes требуют доступного объявленного адреса и должны размещаться в разных доменах отказа, если пул должен обеспечивать устойчивость.

## Проверка и очистка

Регистрация завершена только когда демон сообщает ожидаемые возможности и поступает первый снимок инвентаря и метрик. Если установка завершается ошибкой до регистрации, изучите локальную службу и логи установщика. Удаляйте ожидающую запись только если отказываетесь от этой идентичности; токен удалённого Node нельзя использовать повторно.

## Ошибки установки

Если команда не может скачать или запустить daemon, проверьте исходящий HTTPS, DNS, системное время, состояние package manager, архитектуру и свободное место. Если daemon запустился, но enrollment не завершился, проверьте доступность Relay, не был ли одноразовый token уже использован и была ли команда запущена для pending Node из текущей модалки. Не создавайте несколько pending-записей и не подставляйте их команды друг в друга.

Node, который зарегистрирован без ожидаемой возможности, не готов к своей роли. Проверьте профильную службу, права на socket или storage, необходимые функции ядра и ограниченные startup-логи daemon. Исправьте prerequisite хоста и дождитесь обновления отчёта; смена Node Type после установки не заменяет корректный профиль.

Если хост был зарегистрирован с неправильной ролью, осознанно выведите эту identity из эксплуатации и создайте новый Node с правильной ролью. Перед удалением убедитесь, что ошибочной identity не назначены ресурсы или операции, и удалите её daemon material с хоста, чтобы она не могла неожиданно переподключиться.

## Безопасность после установки

Считайте сгенерированную команду установщика краткоживущим credential. Запускайте её только на целевом хосте, не вставляйте в общий чат или постоянную shell automation и удаляйте из операционных заметок после enrollment. Установленный сертификат daemon становится постоянной identity; его нельзя копировать на другую машину или восстанавливать одновременно на двух активных хостах.

Ограничьте локальный доступ к конфигурации daemon, материалу сертификата, registry credentials, database storage и профильным sockets. Enrollment устанавливает доверие между Gateway и хостом, но не усиливает защиту несвязанных служб ОС. Примените корпоративный baseline хоста и не расширяйте поверхность атаки роли сверх документированных prerequisites.
