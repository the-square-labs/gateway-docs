Gateway наблюдает за состоянием плоскости управления, Nodes, рабочих нагрузок, поведением Ingress, базами данных, активностью сборок, использованием Inference и событиями безопасности.

В продукте нет единого универсального экрана Observability. Эта страница описывает операционную модель, распределённую между Dashboard и страницами Nodes, Routes, workloads, баз данных, builds, Tasks, уведомлений, аудита и status pages. Технический руководитель должен использовать эти сигналы для ответа на три вопроса: затронуты ли клиенты, кто должен действовать и как будет подтверждено восстановление?

Цель — не максимальный объём телеметрии, а небольшой набор надёжных сигналов с назначенными владельцами, полезным хранением и проверенным путём от обнаружения до клиентского восстановления. Gateway предоставляет продуктовые и инфраструктурные сигналы; владельцы сервисов по-прежнему определяют бизнес-критерии успеха, service-level objectives (SLO), эскалацию и мониторинг внешних зависимостей.

Используйте состояние ресурсов для текущей картины, метрики для тенденций, логи для диагностики, долговечные Tasks для прогресса операций, уведомления для действий, status pages для коммуникации с клиентами, аудит для атрибуции и SIEM для внешнего анализа безопасности.

Проектируйте оповещения вокруг устойчивого влияния на клиентов и значимых переходов состояния. Не дублируйте каждое низкоуровневое событие в канал уведомлений.

## Определите владение и успех

Для каждого важного сервиса назначьте business owner, technical owner, on-call destination и владельца коммуникации с клиентами. Определите **доступность** с точки зрения пользователя, а не одного внутреннего badge процесса. Route может быть healthy, пока приложение или база возвращает непригодные ответы; Node может быть online, пока один клиентский путь сломан.

Используйте SLO — измеримую цель надёжности во времени, — чтобы решать, какие условия требуют alerts, а какие должны оставаться только в dashboards или отчётах. В самом alert указывайте ожидаемую проверку восстановления. Успех достигнут, когда клиентский путь снова работает, сигнал восстановился, а временная mitigation удалена.

## Типы сигналов

| Сигнал | Лучшее применение | Распространённая ошибка |
| --- | --- | --- |
| Health | Текущая готовность сервиса | Считать один зелёный badge доказательством сквозной доступности |
| Metrics | Ёмкость и тенденции | Оповещать о каждом кратковременном всплеске |
| Logs | Подробная диагностика | Отправлять секреты или неограниченные payloads |
| Tasks | Долговечный прогресс операции | Считать принятую Task уже завершённой |
| Events | Переходы состояния ресурсов | Использовать объём событий как метрику состояния |
| Audit | Кто и что изменил | Заменять операционные логи записями аудита |
| Notifications | Действие оператора | Пересылать каждое информационное событие |
| Status pages | Коммуникация с клиентами | Публиковать приватную топологию или сырые ошибки |

## Создайте операционное представление

1. Начните с видимых клиентам Routes и бизнес-сервисов.
2. Сопоставьте каждому сервису его Ingress, рабочую нагрузку, базу данных, хранилище и внешние зависимости.
3. Определите health signal и SLO, отражающие влияние на клиентов.
4. Добавьте оповещения о ёмкости ресурсов с устойчивыми окнами.
5. Направьте срочные события в destination с назначенным владельцем.
6. Создавайте публичный status component только для информации, которую должны видеть клиенты.
7. Проверяйте сбой и восстановление, а не только доставку уведомления.

## Процесс диагностики

Используйте Dashboard для первичной оценки, затем откройте затронутый ресурс. Сравните текущее состояние с последними метриками, Tasks, событиями и логами. Сопоставляйте по стабильному ID ресурса, ID операции, request ID и времени. Если отображаемое состояние основано на кэшированном снимке, восстановите соединение владеющего Node до изменения ресурса.

Для мониторинга баз данных сбор начинается в фоне после bootstrap Gateway и когда управляемая база данных становится готова; открывать страницу базы данных не требуется. Первый визит может кратковременно ожидать историю или первый реальный снимок, но не должен придумывать здоровое состояние при отсутствии данных.

Во время инцидента начинайте с затронутого клиентского пути и двигайтесь внутрь: публичный DNS и TLS, Route и Ingress, workload, приватные зависимости, storage и внешние сервисы. Используйте Tasks, чтобы отличить принятую операцию от завершённой. Используйте audit для понимания изменений конфигурации, а не как замену runtime logs.

## Проверяйте саму наблюдаемость

Наблюдайте за путём мониторинга: свежестью Nodes, состоянием ClickHouse, доставкой очереди уведомлений, публикацией status pages, возрастом outbox SIEM и хранением данных. Система наблюдаемости, которая незаметно перестала собирать данные, должна создавать отдельное предупреждение платформы.

Храните телеметрию достаточно долго для реконструкции инцидентов, но применяйте явные бюджеты срока и объёма. Не используйте логи как неконтролируемый архив данных.

## Для операторов: устаревшие и противоречивые сигналы

У каждого health-решения есть timestamp и владелец. При отключении Node его последний snapshot может устареть; восстановите владеющий Node до изменения ресурсов на основании старой информации. Если предупреждение sidebar и detail page расходятся, сравните их source, timestamp и правило агрегации, а не считайте любой цвет безусловно правильным.

Считайте отсутствующие данные неизвестным состоянием, а не здоровым. Проверьте, что collection продолжается, timestamp нового sample меняется, ClickHouse доступен там, где ожидаются structured logs, notification queues опустошаются, а публичные status updates публикуются. После ремонта повторите исходную end-to-end проверку и задокументируйте слепую зону, которая задержала обнаружение.
