Структурированное логирование централизует поддерживаемые события Gateway и daemon с полями для поиска и политикой хранения. Рассчитайте хранилище для приёма и хранения, наблюдайте за состоянием ClickHouse и планируйте обновления движка до прекращения поддержки старых images.

Используйте structured logging, когда командам нужна единая управляемая поверхность поиска вместо несвязанных text files, а SIEM export — когда security operations нужен сокращённый audit stream во внешнем collector. Это связанные, но разные функции: application и platform logs помогают эксплуатационной диагностике; SIEM передаёт уменьшенные с точки зрения privacy события аудита для security analysis. Включение одной функции не делает другую резервной копией.

Владелец платформы предоставляет capacity ClickHouse и limits хранения, владельцы сервисов определяют полезные fields и классификацию данных, а security owner одобряет SIEM destinations и authentication. Успех означает, что известное событие можно принять, найти, хранить нужный срок, сопоставить без секретов и, если требуется, безопасно доставить внешнему collector.

Destinations SIEM доставляют события аудита через долговечный outbox. Отключение SIEM приостанавливает новую доставку, не удаляя конфигурацию destination или исторические terminal records. Проверяйте подписи, повторы, идемпотентность и ёмкость получателя.

Логи и payloads SIEM не должны содержать пароли, токены, закрытые ключи, URI подключений к базам данных, prompts, output моделей или сырые учётные данные привязок. Используйте request IDs и стабильные идентификаторы ресурсов для корреляции.

## Решения до подключения данных

Определите, какие сервисы могут писать, какие fields разрешены, как долго хранятся данные, кто может выполнять поиск и какие события требуют внешнего export. Оценивайте объём через events per second, средний размер события и retention, а не выбирайте произвольный TTL. Более долгий срок даёт больше истории инцидентов, но увеличивает стоимость хранения и последствия сбора чувствительных данных.

Осознанно выберите schema mode:

| Режим | Когда использовать | Компромисс |
| --- | --- | --- |
| `reject` | Качество fields должно строго проверяться при ingest | Producers должны корректно обрабатывать отклонённые события |
| `strip` | Важны известные fields, а неизвестные custom data нужно удалить | Неожиданный диагностический контекст теряется |
| `loose` | Командам нужны гибкие sanitised custom fields | Governance и единообразие поиска требуют большей дисциплины |

Создавайте отдельное logging environment для приложения или значимой trust boundary. Не используйте один ingest token для несвязанных команд; tokens являются write-only secrets и должны независимо отзываться.

## Процесс структурированного логирования

1. Включите функцию и проверьте состояние ClickHouse.
2. Создайте logging environment для одного приложения или границы доверия.
3. Подключите schema, когда требуется валидация полей, или осознанно используйте loose mode.
4. Задайте бюджеты хранения и запросов/событий, соответствующие ожидаемому трафику.
5. Создайте write-only ingest token и сохраните его в secret manager приложения.
6. Отправьте синтетическое событие с известными полями и request ID.
7. Найдите событие и проверьте timestamp, severity, labels и состояние хранения.

Ограничения запросов и событий независимы. Пакетный приём может принять корректные события и отклонить некорректные элементы, поэтому клиенты должны проверять структурированный ответ, а не считать весь пакет успешным.

Официальный TypeScript SDK умеет выполнять batching, retries, flush и передавать trace или request context для Node.js services. Независимо от клиента задайте fallback при временной недоступности Gateway и ограничьте локальный buffering, чтобы сбой логирования не исчерпал memory или disk приложения.

## Хранение и ёмкость

TTL окружения — только одна граница. Housekeeping Gateway также применяет глобальные бюджеты строк и приблизительного размера диска. Отслеживайте доступность ClickHouse, нагрузку merge, рост диска, отклонённый приём и возраст самого нового события. Планируйте хранение исходя из требований инцидентов и compliance, а не оставляйте его неограниченным.

Отключение структурированного логирования скрывает обычные поверхности продукта и отклоняет новый приём, сохраняя данные и конфигурацию. Включайте его снова только после понимания причины состояния или ограничения по тарифу.

Успешная capacity — это не только healthy процесс ClickHouse. Проверьте, что timestamp новейшего события движется, поиск возвращает ожидаемые свежие данные, retention удаляет старые partitions, а ingest rejects объяснимы. Gateway может приостановить ingest при исчерпании настроенной capacity, сохраняя существующий поиск; предупреждение должно сработать раньше этой границы.

## Доставка SIEM

Настройте каждый HTTPS collector с самым узким поддерживаемым методом аутентификации. Проверьте доверие к сертификату, подпись запроса, идемпотентность получателя, допустимый размер пакета, поведение повторов и долговечную историю доставки. Outbox фиксирует прогресс доставки, поэтому временный сбой collector не требует от операторов вручную пересоздавать события.

Если SIEM отключён или право по тарифу потеряно, конфигурация destination и исторические terminal records сохраняются. До возобновления обычной работы подтвердите последнее принятое получателем событие и возраст очереди Gateway.

## Для операторов: контракт доставки SIEM

SIEM destinations должны использовать HTTPS и могут аутентифицироваться bearer token, HMAC-SHA256 или одним проверенным custom header. HMAC-запросы содержат timestamp и signature точного raw JSON body; получатель должен сравнивать подписи за постоянное время и отклонять устаревшие timestamps. Не помещайте credentials в URL, query string, логи или тестовые tickets.

Gateway доставляет через долговечный outbox и повторяет временные network errors, timeouts, rate limits и server failures. Другие client errors могут стать terminal failures. Используйте **Send test event** для проверки destination; синтетический тест не создаёт audit event или queued delivery. Удаление destination удаляет outstanding rows, а отключение приостанавливает delivery для последующего возобновления.

## Правила обработки данных

Определите allowlist полей, которые приложения могут отправлять. Маскируйте у источника, поскольку последующее хранение и экспорт увеличивают последствия утечки секрета. Используйте resource IDs, request IDs, trace IDs и ограниченные категории ошибок вместо сырых учётных данных, prompts, дампов environment или произвольных тел запросов.

Если секрет попал в logging, остановите дальнейшую отправку, отзовите или ротируйте секрет у источника, ограничьте доступ к затронутому environment и следуйте процессу удаления данных и incident response организации. Удаление результата из интерфейса поиска не доказывает, что все retained partitions, exports или внешние SIEM copies исправлены.
