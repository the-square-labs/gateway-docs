# Области, API-токены, OAuth и MCP

Пользователи управляют API-токенами в **Profile > Authorizations > API Tokens**. Секреты показываются один раз. Храните их в secret manager, назначайте минимальные области и отзывайте неиспользуемые токены.

OAuth-клиенты делегируют полномочия пользователя с явными redirect URI и consent. Remote MCP использует ту же модель ресурсов и областей, что REST и Console; это не привилегированный обходной путь.

Используйте отдельные учётные данные для CI, мониторинга и интерактивных инструментов. Избегайте долговечных токенов администратора. Ограничивайте автоматизацию точными Nodes, Routes, рабочими нагрузками, базами данных или Pages Projects, которыми она владеет.

Обычные API-учётные данные `gw_` и учётные данные OAuth не попадают в плоскость данных Gateway Inference. Inference использует отдельные пользовательские токены `gwi_`.

Фиксируйте создание, использование и отзыв токенов в аудите. Ротируйте сразу после подозрения на раскрытие и отдельно проверяйте активные сеансы.

## Выберите тип учётных данных

| Учётные данные | Использование |
| --- | --- |
| Session | Интерактивный доступ к Operations Console |
| API token | Прямая автоматизация, принадлежащая одному пользователю Gateway |
| OAuth client | Делегированная авторизация пользователя и сторонние приложения |
| Remote MCP OAuth | Клиенты инструментов, работающие через поверхность MCP Gateway |
| Inference token | Запросы к отдельной плоскости данных Gateway Inference |

Не подменяйте один тип другим только потому, что его проще скопировать. Тип учётных данных определяет consent, отзыв, оценку областей, назначение аудита и семейство доступных endpoints.

## Создайте токен с минимальными правами

1. Определите точные операции и ресурсы, которыми владеет автоматизация.
2. Создайте отдельного пользователя или service identity, когда атрибуция должна быть раздельной.
3. Назначьте минимальные глобальные области и области ресурсов.
4. Создайте токен и один раз сохраните секрет.
5. Поместите его в secret manager и внедряйте во время runtime.
6. Проверьте один разрешённый и один запрещённый запрос.
7. Зафиксируйте владельца, назначение, ожидания срока действия/ротации и зависимую систему.

Не встраивайте токены в URL репозитория, историю команд, screenshots или логи. Замаскированное значение UI нельзя получить повторно; при утрате секрета создайте замену и отзовите старый токен.

## OAuth и MCP

Регистрируйте точные redirect URI и запрещайте wildcard redirect. Проверяйте запрошенные области при consent и отделяйте клиенты разработки от production-клиентов. Инструменты Remote MCP используют те же проверки авторизации и видимость ресурсов, что REST и Console; обнаружение инструмента не выдаёт право на его выполнение.

Обрабатывайте ошибки авторизации раздельно:

- `401`: аутентификация отсутствует, истекла или недействительна;
- `403`: аутентифицированной идентичности не хватает области или права по тарифу;
- `409`: текущее состояние ресурса или quota конфликтует с операцией;
- `422`: запрос не прошёл валидацию.

## Ротация и реагирование на инциденты

Создайте замену, обновите зависимую систему, подтвердите успешное использование и только затем отзовите старые учётные данные. При подозрении на раскрытие сначала отзовите их, если это операционно безопасно, проверьте активность аудита, отдельно аннулируйте связанные сеансы и ротируйте любой downstream-секрет, который мог быть раскрыт.
