Этот сценарий оставляет базу данных неопубликованной и предоставляет приложению идентичность, выделенную для binding.

## Основной сценарий

1. Зарегистрируйте выделенный database Node.
2. Откройте **Databases** и создайте PostgreSQL, Redis или ClickHouse из поддерживаемого каталога.
3. Оставьте **Publish TCP** отключённым, если прямой внешний доступ не является осознанным требованием.
4. Дождитесь, пока подготовка и проверки состояния достигнут **Ready**.
5. Откройте целевой Container, Deployment или Compose service и создайте managed database link.
6. Выберите базу данных и параметры binding.
7. Пересоздайте или заново разверните рабочую нагрузку, когда интерфейс укажет, что нужно применить материалы окружения или сети.
8. Выполните запрос из приложения и проверьте эксплуатационные данные binding.

![Контейнер приложения со здоровым подключением к управляемой базе данных](/screenshots/product-tour/container-secure-link.png)

## Ожидаемые гарантии

- Рабочая нагрузка не получает учётные данные владельца базы данных.
- Каждый binding получает отдельную engine identity.
- Пересоздание рабочей нагрузки сохраняет binding.
- Удаление binding выводит его identity из эксплуатации, не удаляя базу данных.
- Сбои базы данных или Relay блокируют новые подключения и восстанавливаются через реконсиляцию.

## Не делайте этого

- Не копируйте учётные данные из внутренних контейнеров.
- Не изменяйте принадлежащие Gateway сети binding или метаданные слушателя через API жизненного цикла Docker.
- Не публикуйте порт базы данных только для диагностики приватного binding.
- Не удаляйте роли базы данных вручную, если только runbook удаления Gateway явно не требует восстановления.
