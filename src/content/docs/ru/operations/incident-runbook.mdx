Этот runbook помогает incident lead защитить клиентский сервис, определить владельца сбоя и выбрать обратимый путь восстановления. Incident lead отвечает за приоритеты и коммуникацию, platform operator — за свидетельства Gateway и managed Nodes, владельцы приложений и баз данных — за проверку своих сервисов. Человек, выполняющий команды, не должен единолично принимать решения о риске.

Успех означает понятное влияние на клиентов, остановку несвязанных изменений, сверенное состояние фактического runtime и проверку восстановления через пользовательский путь. Зеленый Dashboard сам по себе не доказывает восстановление.

## Первые пять минут

1. Зафиксируйте время начала, затронутый клиентский путь и недавние изменения.
2. Проверьте состояние Gateway, PostgreSQL, Redis и Relay.
3. Определите, затрагивает ли проблема плоскость управления, Ingress, один Node, одну рабочую нагрузку или общую зависимость.
4. Заморозьте несвязанные изменения.
5. Используйте режим обслуживания или инцидент status page, когда влияние на клиентов подтверждено.

## Relay недоступен

Проверьте службу Relay, volume идентичности, доступность базы данных, версию image и публичный `9443/tcp`. Не возвращайте порт приложению и не обходите авторизацию новым публичным listener.

## Node offline

Существующие рабочие нагрузки могут продолжать работу. Проверьте питание/сеть хоста, службу daemon, время, идентичность сертификата и исходящую доступность Relay. Не выполняйте мутации на основе устаревшего инвентаря.

## Неудачный релиз

Для Deployments откатитесь на предыдущий исправный слот. Для Pages переместите Tag. Для Containers, собранных из Git, повторно разверните последний одобренный digest. Сохраните логи и историю операций.

## Сбой привязки базы данных

Проверьте Relay, оба Node, состояние базы данных, желаемое состояние привязки, состояние listener целевого daemon и principal движка. Повторите реконсиляцию до ручных изменений идентичности; отдельного контейнера коннектора базы данных для каждой привязки не существует.

## Завершение инцидента

Подтвердите восстановление из внешнего клиента, намеренно снимите режим обслуживания, документируйте первопричину и пробел обнаружения и создайте последующую работу для каждого временного смягчения.

## Плоскость управления недоступна

Проверьте Container/process Gateway, PostgreSQL, Redis, persistent volumes, давление диска, миграции и логи приложения. Сохраните существующие ключи шифрования и базу данных до попытки создать заменяющий экземпляр. Если клиентские рабочие нагрузки продолжают работу, избегайте широких изменений хоста во время восстановления плоскости управления.

После возврата Gateway проверьте вход, расшифровку, состояние Relay, фоновые задания, обнаружение обновлений, уведомления и свежие снимки Nodes. Не считайте daemon реконсилированными только потому, что Dashboard загрузился.

## Сбой Ingress

Следуйте [Диагностике Ingress](/ru/ingress/troubleshooting/) от DNS через сеть, TLS, применение nginx, состояние Route и upstream. Используйте режим обслуживания, когда virtual host должен оставаться стабильным во время ремонта. Сохраняйте ошибки валидации сгенерированной конфигурации и свидетельства внешних запросов.

## Операция рабочей нагрузки зависла

Проверьте долговечную Task, соединение владеющего Node, историю операций daemon, ресурс runtime и ID запроса/операции. Timeout браузера не доказывает сбой команды. Реконсилируйте первую операцию до запуска дублирующего create, recreate, migration или delete.

Если доступен Force Cancel, разберитесь, отменяет ли он только ожидание Gateway или также отправляет отмену владельцу. После отмены обновите состояние runtime и очищайте marker прерванной операции только через поддерживаемый путь реконсиляции.

## База данных недоступна

Разделяйте сбои состояния движка, хранилища, прямой публикации, управляемой привязки и запроса приложения. Проверьте Database Node, engine Container, storage image/mount, снимок мониторинга, путь Relay, целевой Docker Node, listener, принадлежащий daemon, идентичность привязки и конфигурацию приложения.

Не удаляйте базу данных или principal движка как диагностический шаг. Сохраните хранилище и историю операций, затем повторите узкую неудачную реконсиляцию.

## Коммуникация и свидетельства

Ведите единую временную шкалу инцидента с UTC timestamps, затронутыми ресурсами, видимым пользователям влиянием, изменениями, IDs Tasks, request IDs, решениями и проверкой. Публичные обновления описывают влияние и прогресс, не раскрывая топологию или сведения безопасности.

## Барьер восстановления

Для восстановления требуется:

- клиентский путь работает извне управляемой сети;
- желаемое состояние Gateway совпадает с текущим состоянием владельца;
- оповещения восстанавливаются по правильной причине;
- ожидающие операции и доставки понятны;
- временная экспозиция или обходы удалены;
- для каждого оставшегося риска назначены владелец и срок.

## Модель решений для incident lead

Предпочитайте действия, сохраняющие свидетельства и уменьшающие blast radius. Приостановите несвязанную автоматизацию до перезапуска общих сервисов. Если control plane недоступна, но workloads продолжают обслуживать трафик, восстанавливайте управление без пересоздания здоровых ресурсов. При сбое Ingress сохраняйте hostname через maintenance mode или проверенный rollback, а не меняйте DNS несколько раз. Если целостность данных неясна, остановите запись до оптимизации доступности.

Немедленно эскалируйте возможное раскрытие credentials, повреждение storage, неизвестное состояние schema migration, потерю Relay identity, несогласованное владение database binding или release artifact без подтверждаемого происхождения. В таких условиях обычный restart может привести к постоянной потере или несанкционированному доступу.

### Таблица свидетельств для оператора

| Свидетельство | Зачем нужно |
| --- | --- |
| Внешние DNS, TLS и ответ приложения | Подтверждает реальное влияние на клиентов |
| Состояние Gateway, PostgreSQL, Redis и Relay | Разделяет сбой control plane и data plane |
| Last seen Node, capabilities и daemon logs | Определяет владельца runtime и устаревший inventory |
| Task, operation и request IDs | Предотвращает дублирующие или неоднозначные изменения |
| Последняя одобренная версия и artifact digest | Дает известную цель rollback |
| Состояние backups баз данных и volumes | Определяет безопасные варианты восстановления |

После восстановления проведите короткий review, пока свидетельства доступны. Зафиксируйте исходное изменение, работу detection, необходимые ручные шаги и проверку, которая выявила бы проблему раньше. Превратите временные инструкции в проверенное изменение runbook, а не сохраняйте недокументированную историю shell.
